Database, domain and WQL performance review

wod-wiki and wod-wiki-api, 2026-10-06. Storage schema, query execution and migration proposal, with measured local evidence and every claim tied to source.

1 Verdict 2 Current inventory 3 Findings 4 Proposed model 5 WQL execution 6 Migration 7 Measured proof

1. Verdict and evidence status

The first fix is to use the indexes already present. Content queries read whole stores and filter in JavaScript. Selective indexed reads can reduce that work without replacing the database or adding an ORM. Compound filtering, counting, ordering and paging need a domain-query endpoint on the SQL API; the generic store wire cannot express them together.

Start with existing by-type and event-range indexes and clean-read count forwarding. Then map catalog parent identities and add relational content selection. Project typed metric facts only when measured metric workloads justify the migration. IndexedDB keeps indexed local reads and exact residual JS semantics.

What was actually measured

Three kinds of evidence back this review, all offline and local.

  • A read-only local SQLite snapshot (Python sqlite3 3.53.1, seven repeated fetches per query, median warm read). Nothing persistent changed. Section 7 lists every query with row counts, bytes and plans.
  • The real QueryService from packages/wql, bundled in memory and run against injected read-only adapters over the same snapshot. Two queries were executed; both are quoted with exact numbers in section 7.
  • The real ApiStorage adapter behind a recording-only transport, which shows one request shape: GET /api/v1/notes/all with no count parameter, 12 fixture rows received, 5 returned. This is instrumentation of the real client adapter, not an API latency test.

Evidence limits. The snapshot is older than the current vendor schema: it has no by-user columns and misses some indexes, so per-store byte counts describe that snapshot, not current writes. The 41-event sample contains zero civil metric dates and an empty events__by_metric_date junction, so metric-date coverage behavior was not exercised and its emptiness is expected for this sample, not a defect. Empty field_values is likewise a sample property. No production, network, API or browser latency is measured, and no speedup is claimed for any runtime surface.

Where queries actually run today

WQL executes in the browser over injected store interfaces. The interfaces expose only whole-store reads for content: getAllNotes(), getAllBlocks(), getAllEfforts() in packages/wql/src/stores.ts:44-56. Datasets such as @session and @today are host-populated memory stages that never touch the database, packages/wql/src/stores.ts:99-104.

  • Note find. runFind concatenates user and static note stores with getAllNotes(), applies predicates in JS, then slices. packages/wql/src/QueryService.ts:1068-1215. Container resolution then issues per-note page lookups, QueryService.ts:1229-1248.
  • Block find. runFindBlock reads all 20,826 block rows, then text, type, catalog, tag, effort and note filters in JS. QueryService.ts:1252-1355. The smoke run in section 7 shows what this costs for a five-row limit.
  • Aggregates. The executor requests timestamp-window and metric-date candidates, QueryService.ts:1439-1472, but the production adapter implements both as full reads followed by JS filters. Projection, metric, range, tag and coverage selection also run in JS.
  • Metric joins. applyMetricJoin rebuilds a note-to-content map by scanning every block row, then reads events per content id. QueryService.ts:1909-1999.
  • Library search. With free text present, entrySearch runs the note query and a companion :block query in parallel, each including upstream pipes, and unions the two by note id. apps/playground/app/lib/entrySearch.ts:199-237.
  • Library list. IndexedDBContentProvider.getEntries hydrates all notes, all page notes, all pages, all tags per note and all segments, reconstructs latest revisions and raw content client-side, then filters and sorts in JS. apps/playground/src/services/content/IndexedDBContentProvider.ts:169-267.
  • Event reads. Only getEventsForNote uses an index, fetching summary-grain rows per result id plus the wellness pseudo-result over by-result-grain, apps/playground/src/services/storage/StorageService.ts:527-537. The other four methods read every event and filter in JS, StorageService.ts:540-562.

The API side already has SQL

wod-wiki-api materializes the same store definitions as SQL tables and pushes down what it can. Range predicates compile to SQL on the first key column, with tuple bounds expanded part-wise; anything unrepresentable falls back to a scan plus in-memory compare. ../wod-wiki-api/src/store.rs:125-223. Indexed reads add ORDER BY and LIMIT in SQL, store.rs:245-310, and writes extract index columns from the payload next to the JSON, store.rs:327-359. The multi-entry junction path is exact-match only, store.rs:277-282. Every selected payload is parsed from JSON on each read, ../wod-wiki-api/src/db.rs:232-254; SQLite runs behind one connection mutex, Postgres behind a pool of four, db.rs:263-297. Routes are generic per-store CRUD plus /tx, with no WQL endpoint, ../wod-wiki-api/src/api.rs:99-165. The deployment is a trusted single-user self-host by design, README.md, deliberate limits.

The important distinction: the SQL engine exists, but the API mimics one-store IndexedDB reads. It does not execute WQL. That is why the smallest first change is indexed candidate fetch and batch plus metadata reads, not a new query service.

3. Prioritized findings

Each finding names the code, the measured cost where one exists, and the smallest change that fixes it. Proposals are proposals; nothing here is implemented.

F1 P0 Content find reads whole stores, then filters in JS

What happens. runFindBlock fetches every block before filtering, QueryService.ts:1252-1313. The note branch of runFind does the same over both note stores, QueryService.ts:1068-1215. BlockQueryStore offers only getAllBlocks(), stores.ts:53-56.

Measured cost. On the real source against the snapshot, :block{type:wod} | limit 5 read 20,826 rows and 7,852,733 JSON bytes to return 5, with 20,694 surviving selection. :note | limit 5 read 989 rows and 299,199 bytes to return 5. Section 7 has the exact numbers. The same snapshot shows the by-type index doing the culling work in 1.683 ms where the full scan takes 12.725 ms, and a fifty-row head of the table returning in 0.018 ms. The index already exists; the query layer cannot reach it.

Proposal. Extend the content read interfaces with indexed candidate selection. A type-only query can fetch all by-type matches instead of all blocks; note and date restrictions can use their existing indexes too. Apply every remaining filter before paging. A bounded page fetch needs a cursor loop until enough matches are found, or a relational query that implements all predicates. An arbitrary over-fetch multiplier is not correct, and global sorting or exact counts may still require the full candidate set.

Boundary. The current wire can read one index with a range and count; it cannot combine the JSON source fence, tags, arbitrary order and limit into one request. The SQL illustration in section 5 therefore needs the proposed domain-query endpoint. Existing index routing is the smaller first patch.

F2 P1 The API client drops count on clean reads

What happens. remoteList accepts a count parameter and forwards it as a query parameter. packages/storage/src/api.ts:74-85. But the store view calls the server without it and slices afterwards: getAll runs overlay(await this.serverRows('all', range), count) with no count argument. api.ts:247-253. The server honors count in SQL when given, ../wod-wiki-api/src/store.rs:245-268.

Observed. With the real adapter behind a recording transport, readonly('notes').getAll(undefined, 5) sent GET /api/v1/notes/all with no count, received 12 fixture rows, and returned 5. The client truncates locally even on a clean read.

Proposal. Forward the requested count when the transaction buffer is clean. The dirty() path must keep fetching enough candidates, because buffered puts, deletes and range deletes can add or remove rows across the whole key order, and the overlay applies in op order. That path needs the server's ORDER BY on key columns, which exists, plus a deliberate over-fetch, to avoid lost or misordered rows. This is a missing forwarding fix, not a missing server LIMIT.

F3 P1 Four event reads ignore their own indexes

What happens. Event indexes already exist, schema.ts:107-117, but four adapter methods read all events and filter in JS, StorageService.ts:540-558. getEventsForNote instead reads only summary grain through the result index. That restriction can hide available detail from note-scoped pipelines and event tables. Preserve its wellness pseudo-result inclusion, but review all-grain note selection before copying this behavior into SQL.

Context. The snapshot holds 41 events, so this is about shape, not today's cost. Aggregate fetch already routes through getEventsByTimeRange and the metric-date union, QueryService.ts:1452-1470, so every windowed aggregate pays a full events scan inside the storage adapter.

Proposal. Route the four methods through their indexes: a range on by-timestamp, exact or range keys on by-result-grain and by-content-grain, and exact-match sets on the multi-entry by-metric-date. Note the API junction is exact-match only, ../wod-wiki-api/src/store.rs:277-282; the IndexedDB multi-entry index does support ranges, so adapters differ and the call sites should ask for what each backend can do.

F4 P1 The metric-date union silently skips windows past 400 civil dates

What happens. Metric-date candidates are unioned only when the date list has at most 400 entries, QueryService.ts:855-862,1459-1468. [INFERENCE] With a truly bounded timestamp fetch, longer windows can miss rows whose metric date is in range but fetch timestamp is outside it. The present adapter's full read still filters by timestamp, so it does not guarantee those rows survive either. The same completeness audit must cover per-metric occurrence instants that differ from the event timestamp.

Evidence status. Not reproduced on the snapshot: zero rows carry civil metric dates, so both branches see empty lists for different reasons. A fixture gate with more than 400 dates is required before any rewrite.

Proposal. In a SQL projection, give each observation its own temporal kind column and select candidates as the union of the timestamp range and the junction over covered dates, with no cutoff. Until then, raise or remove the cutoff behind a fixture that proves completeness for long windows. Do not treat the event timestamp as canonical for every metric; the summary below keeps the two anchors distinct on purpose.

F5 P1 Catalog block rows live in a different identity namespace than notes

What the snapshot shows. 20,813 of 20,826 block rows reference a catalog path parent, not a note UUID. Only 13 rows match user notes and exact segments. Zero of 748 distinct static parent keys match any of 987 distinct note source paths. All 7,462 effort links match on block content id plus note id, not on an occurrence identity. These are namespace facts about how seed data is generated and imported, not corruption, and the migration must resolve the namespace before any relational join is proposed.

Where the namespace comes from. The seed generator writes collection rows with noteId set to a path-derived stem and segmentId to a parsed section id, feeds rows to a route key, and guide rows to the frontmatter route. scripts/generate-seed.ts:223-334. The importer maps the full source path to a fresh note UUID with its own algorithm, writes one full-markdown segment per imported note, and copies block index rows untouched. apps/playground/src/services/seed/SeedImporter.ts:35-50, 69-135, 208-236. Virtual notes synthesized from block rows coexist with the seeded UUID documents, apps/playground/src/services/content/staticBlockIndex.ts:88-120. The legacy noteId on a block row and the imported UUID are simply different keys.

Proposal, smallest model. Add the full source path to generated block rows and map it to the existing imported note's sourcePath. The 748 observed parent keys are not 20,813 separate notes. Completeness and uniqueness of that map must be verified against the manifest before cutover; this review did not prove every parent has an imported counterpart. Preserve route aliases separately. Static parsed sections must not foreign-key their legacy section id to the single full-markdown segment the importer writes.

Constraint carried forward. Nothing may foreign-key a legacy block row's noteId to notes until the mapping exists. Effort links matching on content id plus note id stay valid evidence of content identity; they say nothing about occurrence identity.

F6 P1 API schema repair never backfills, so upgraded databases drift

What happens. ensure_schema creates tables if missing, then patches missing key and index columns onto older tables with ALTER TABLE ADD COLUMN, and creates missing indexes with IF NOT EXISTS. ../wod-wiki-api/src/schema.rs:98-193. The ALTER path adds the column but does not recompute it from the JSON payload, and CREATE INDEX IF NOT EXISTS will not replace an index whose keyPath definition changed. The consequence, by inference from that code: rows written before a schema change keep their old extracted columns and stay invisible under the new index until each row is re-put or a backfill runs. Nothing measures this on the current snapshot, and it should not be claimed as an observed failure.

Type drift too. The Postgres numeric allowlist hardcodes seven columns, ../wod-wiki-api/src/schema.rs:63-92. It omits page.by-date, which in the current domain is a civil date string, so the lesson is not "make everything numeric" but that an allowlist keyed to index names will keep diverging from the vendored schema as definitions change.

Proposal. Introduce versioned migrations with a schema digest: on version change, backfill extracted columns from payload, drop and recreate changed indexes, and reconcile a digest recorded in meta. This belongs in the API repo; the browser keeps IndexedDB versioning it already has. The vendored schema.json regenerates as part of the same gate so the two sides cannot drift.

F7 P2 Write-path integrity: duplicate tag links, incomplete cascade, scalar delete on a compound key

Duplicate tag links. The snapshot holds 10 duplicate note_tags (noteId, tagId) groups. note_tags is an ordinary relation store with its own row id and no pair constraint, packages/storage/src/schema.ts:64-68, not a multi-entry junction, so "duplicates are harmless junction dedup" is wrong. Reads happen to dedupe through Set-building, QueryService.ts:1121-1128, but counts, joins and any future unique constraint will not. Deterministic dedupe first, then add the pair constraint.

Cascade misses containment. deleteNote removes the note plus sessions, results, events, segments and related rows in one transaction, but does not touch block_efforts. apps/playground/src/services/storage/StorageService.ts:81-119. Stale containment rows after note deletion is an inference from the code, not a reproduced defect, but a relational migration must add the cleanup guard. The whole-note deletion intent is correct and must be preserved; what must not happen is a cascade that destroys saved run history when an editor merely retires a live query section.

Scalar delete on a composite key. Segment deletion passes row.id alone although the store key is (id, version). StorageService.ts:95-98 against the keyPath at packages/storage/src/schema.ts:70-77. This is a correctness risk to name and test, not an experimentally proven bug.

Revisions are not immutable. Non-content edits such as position, type or source-content changes mutate the same revision row in place, apps/playground/src/services/content/IndexedDBContentProvider.ts:650-657. Any proposal that claims immutable segment revisions must say which fields it freezes and which stay mutable, instead of asserting immutability the code does not have.

F8 P2 Predicate parity: source-kind overlap, per-key OR, and the entry-search union

Source kinds overlap. sourceMatches accepts guides:* for both the page and guide kinds, and page:collection:* for both collection and page. packages/wql/src/QueryService.ts:112-133. A proposed source_kind column therefore cannot hold one mutually exclusive category. Canonical provenance, where a row really came from, must be materialized separately from WQL source membership, which keeps the overlap and lets the compiler expand kind predicates into unions.

Filter algebra differs by path. Aggregate matching treats filters as OR within a key and AND across keys. The block find loop applies each filter clause in sequence, which ANDs even repeated keys. QueryService.ts:1269-1313 versus QueryService.ts:1632-1678. Any SQL translation must pick one semantic per call site and test parity per target. Do not promise universal OR equivalence without those tests.

Entry search unions two limited results. The note query and the companion block query each include upstream pipes, are limited independently, and merge by note id. apps/playground/app/lib/entrySearch.ts:199-237. A single selection plan, one CTE for title OR body, then count and order, then one page, then bounded previews and tags, changes pagination semantics deliberately: total counts and per-page composition will differ from the union of two separately limited sets. That is a product decision to make explicitly, including what the UI's matched count should mean, not a silent rewrite.

F9 P2 Native substring search needs capability checks, not assumptions

The bar. Current WQL text matching is a lowercased JS includes on raw content, packages/wql/src/QueryService.ts:1265-1268. Any native replacement must preserve literal substring semantics for short inputs, %, _, backslashes, and Unicode case.

Engines. SQLite FTS5's trigram tokenizer supports substring-like matching for terms of three or more characters, but a LIKE ... ESCAPE expression cannot use the trigram index, so literal special characters require a different plan. sqlite.org FTS5, trigram tokenizer. Postgres pg_trgm gives indexable similarity and substring support with GIN or GiST. postgresql.org pg_trgm.

Working shape. Index a copy normalized with the current JS toLowerCase() rule, use trigram candidates, and recheck literal substring membership. Short inputs still work through a structurally scoped scan; without other predicates that scan may remain large. The prototype imported all 20,826 blocks, matched 1,301 IDs for one ASCII term, and returned a 50-row page in 0.918 ms median. This proves one input class on Python's SQLite, not deployed engine support.

Open checks. The deployed libsql build's tokenizer capability must be verified; a local Python test is not proof. FTS virtual tables and pg_trgm DDL cannot fall out of the STORE_DEFS generator, so the search DDL needs its own versioned migration. Escaping parity tests must cover %, _, \, combining marks, and case folding differences between JS and each engine.

F10 P3 The query cache is intentionally unwired; keep it that way until reads are bounded

The module says so itself: no production consumer, awaiting cutover, with structural cache keys and a coalescing helper. packages/wql/src/queryCache.ts:1-33. Reuse it only after bounded reads exist and mutation invalidation is wired, since caching whole-store scans would mask the problem this review is about. The fix is moving relational work into the storage layer, not hiding it behind a cache.

4. Proposed canonical model

Everything in this section is a proposal. Nothing here exists in either repo, and none of it has been measured. The model reuses the current stores, keeps payload JSON for replay and editing, and projects only fields that queries actually need into typed relational rows.

Design rules. Additive first, cutover later. One occurrence row per placed block, one content row per Block Content Id, so the same workout at two positions keeps two occurrences. Query-source identity maps through the imported UUID notes and their source paths, with no separate catalog document entity and no mass creation of notes. Sessions stay metadata for active runs; events remain the authoritative statement stream. Metric observations get a typed projection with evidence, never synthetic zeros, and identity reuses the existing deterministic fact id so consumer dedupe does not change.

Concrete tables (proposal)

The SQL below illustrates SQLite domain projections, not a ready-to-run migration. PostgreSQL migrations must use DOUBLE PRECISION for numeric observation values and epoch milliseconds, integer revision/position columns, and compatible referenced key types. Keep shared domain field definitions in the storage contract and explicit engine DDL in the API. Do not force native projections through the generic PostgreSQL TEXT-default index generator. Add strong foreign keys only after ownership, backfill and delete policies pass.

Segment head pointer and revision resolution

Today every reader folds latest revisions in memory with version > comparison, then filters history. apps/playground/src/services/storage/StorageService.ts:399-412. The order matters and is easy to get wrong in SQL: filtering is_history before taking MAX(version) resurrects a superseded revision. A checked fixture proves it, shown in section 7. Legacy rows may also lack the flag entirely, so the SQL form must coalesce.

-- proposal: head pointer over existing segments (id, version)
CREATE TABLE segment_head (
  id              TEXT NOT NULL,
  note_id         TEXT NOT NULL,
  current_version INTEGER NOT NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (id, current_version) REFERENCES segments (k0, k1)
);
CREATE UNIQUE INDEX idx_segment_head_note ON segment_head (note_id, id);

-- correct current-content resolution: MAX first, history filter second,
-- with COALESCE for rows written before the flag existed.
SELECT s.data FROM segments s
JOIN segment_head h ON h.id = s.k0 AND h.current_version = s.k1
WHERE h.note_id = :note_id
  AND COALESCE(s.i_by_history_0, 0) = 0
ORDER BY json_extract(s.data, '$.position'), s.k0;

The in-place mutation behavior for non-content edits, finding F7, means the head pointer is maintained by the write path, not assumed stable.

Query-source identity: source path mapping, no new entity

Reuse imported UUID notes where a complete source-path map can be established. Verify all 748 observed static parent keys against the seed manifest; unresolved or ambiguous parents block relational cutover. Do not guess by trimming route strings.

-- proposal: on the existing notes table
ALTER TABLE notes ADD COLUMN source_path TEXT;      -- e.g. markdown/collections/girls/fran.md
CREATE UNIQUE INDEX idx_notes_source_path ON notes (source_path)
  WHERE source_path IS NOT NULL;

-- block rows gain the parent path at generation or import time,
-- so resolution is a deterministic map, not string trimming:
-- block_index payload gains source_path; resolution =
--   notes WHERE source_path = :block_source_path
-- legacy row.noteId stays as-is and is never joined to notes.id
-- until the map exists. Occurrence identity is separate:
-- same content at two positions = two occurrence rows below.

Existing sourcePath values on legacy rows are not the same string as the legacy noteId, so no cross-namespace equality is assumed anywhere.

Query block occurrence, content identity and containment

The Block Content Id already survives moves and clones by design, CONTEXT.md, Block Content Id. The proposal separates the content identity from the placed occurrence so history stays attached to content while position edits touch only occurrences.

-- proposal: content identity table keyed by existing Block Content Id
CREATE TABLE block_content (
  content_id TEXT PRIMARY KEY NOT NULL
);

-- replacement read projection for block_index, not another authority.
-- Prose and headings have no workout content identity.
CREATE TABLE query_block (
  occurrence_id TEXT PRIMARY KEY NOT NULL,
  parent_note_id TEXT NOT NULL,   -- resolved notes.k0 after mapping
  content_id TEXT REFERENCES block_content(content_id),
  section_key TEXT NOT NULL,
  ordinal INTEGER NOT NULL CHECK(ordinal >= 0),
  data_type TEXT NOT NULL,       -- wod, markdown, frontmatter, h1...
  source_path TEXT,
  source_id TEXT,                  -- preserve WQL source overlap
  effective_date REAL NOT NULL,    -- parent date/createdAt fallback
  normalized_text TEXT NOT NULL,  -- JS toLowerCase(rawContent)
  payload TEXT NOT NULL,          -- current block presentation/evidence
  UNIQUE(parent_note_id, section_key)
);
CREATE INDEX idx_query_block_type ON query_block(data_type, effective_date, occurrence_id);
CREATE INDEX idx_query_block_parent ON query_block(parent_note_id, ordinal);
CREATE INDEX idx_query_block_content ON query_block(content_id);

-- only add this normalization when existing block_efforts is replaced.
-- Interpretation may change without changing Block Content Id.
CREATE TABLE content_effort (
  content_id TEXT NOT NULL REFERENCES block_content(content_id),
  effort_slug TEXT NOT NULL,      -- references efforts.k0 after validation
  parser_ver TEXT NOT NULL,
  PRIMARY KEY(content_id, parser_ver, effort_slug)
);
CREATE INDEX idx_content_effort_slug ON content_effort(effort_slug, parser_ver);
Sessions, events and typed metric facts

Sessions are metadata for active runs; live sessions hold metadata only and the statement stream lives in event rows, with legacy results rows carrying inline logs. apps/playground/src/services/catalog/fieldCatalog.ts:108-155. Wellness rows use the pseudo id wellness:<noteId>, which is not a session, so no unconditional session foreign key is allowed.

-- proposal: typed observation projection over retained event payloads
-- fact identity reuses the deterministic current id so consumer dedupe
-- is unchanged: fact_id = '<event.id>:<factOrdinal>'
-- (packages/wql/src/derivation.ts:324-327, 432-438). One event can hold
-- several facts; observation count is not event count.
CREATE TABLE metric_fact (
  fact_id        TEXT PRIMARY KEY,
  event_id       TEXT NOT NULL,
  result_id      TEXT NOT NULL,   -- includes wellness pseudo-results
  session_id     TEXT,                     -- nullable; wellness rows have none
  origin         TEXT,                     -- preserve recorded journal/playground/user origin
  content_id     TEXT,                     -- blockContentId when present
  note_id        TEXT,
  field_path     TEXT NOT NULL,            -- typed field ref: path
  field_kind     TEXT NOT NULL,            -- existing FieldRef kind, numeric facts use number
  field_dim      TEXT,                     --   physical dimension
  value          REAL NOT NULL,
  unit           TEXT,
  unit_evidence  TEXT,                     -- JSON: original unit and conversion used
  temporal_kind  TEXT NOT NULL CHECK(temporal_kind IN('instant','civil-date')),
  occurred_at    REAL,                     -- exact observation instant, epoch ms
  civil_date     TEXT,                     -- recorded YYYY-MM-DD, not UTC midnight
  grain          TEXT NOT NULL CHECK(grain IN('event','summary')),
  representation TEXT NOT NULL CHECK(representation IN('direct','substitute')),
  coverage       TEXT,                     -- retained SummaryCoverage JSON
  reducer_stats  TEXT,                     -- retained ReducerStats JSON
  effort_slug    TEXT,
  group_tags     TEXT,
  CHECK((temporal_kind='instant' AND occurred_at IS NOT NULL AND civil_date IS NULL)
     OR (temporal_kind='civil-date' AND civil_date IS NOT NULL AND occurred_at IS NULL))
);

Reuse projectEventToFacts for identity, field normalization, temporal evidence and representation classification. Preserve grain separately; one event can contain several observations. The field catalog remains discovery, not a second numeric metric registry. The projection must retain resultId for every population, including wellness pseudo-results, and the coverage partition, unit and context evidence used by selectContributions. Store no synthetic zeros. Only index measured access patterns; start with time and content plus typed field identity, then inspect plans before adding the others. Add a normalized fact_dimension(fact_id,key,value) relation only when actual custom-dimension predicates justify moving them out of retained JSON.

5. WQL execution changes

First route selective reads through existing indexes. Then add a validated relational-query read for compound predicates, metadata and pages. Numeric projection is a separate measured step. Illustrations use SQLite named parameters; PostgreSQL binds positional values and uses engine-specific expressions.

Stage plan

  1. Minimum first patch. Indexed candidate fetch using existing by-type and range indexes, batch and metadata reads before content. No semantics change, no new indexes.
  2. Query boundary and metadata. Count, order, limit, pagination and bounded previews execute at the storage boundary; the API gains a validated read-only domain read. This is an additional planned domain read alongside the existing generic routes and the /tx write batch, which stays as it is.
  3. Measured metric projection. The typed metric_fact projection from section 4 feeds aggregates once identity mapping exists.

Bounded candidate fetch, stage one shape

This snapshot-only illustration proves indexed type selection can bound transfer. It is not a complete translation of sourceMatches, default order or the WQL source fence. It must not replace the executor without parity tests. The current generic wire cannot execute this whole SQL statement.

SELECT data FROM block_index
WHERE i_by_type_0 = :type
  AND (json_extract(data, '$.sourceId') IS NULL
       OR json_extract(data, '$.sourceId') IN ('journal', 'playground', 'page')
       OR json_extract(data, '$.sourceId') LIKE 'collection:%'
       OR json_extract(data, '$.sourceId') LIKE 'page:%'
       OR json_extract(data, '$.sourceId') LIKE 'guides:%')
ORDER BY k0
LIMIT :limit;

Observed plan: indexed type search plus temporary sort, 5 rows and 2,125 JSON bytes. No elapsed time recorded for this illustration. Stage one can instead route a type predicate to getAllFromIndex('by-type', ...), then apply the exact remaining JS predicates. Page only after filtering; cursor continuation or full candidate selection is required where remaining predicates or global ordering demand it.

Tags: EXISTS and NOT EXISTS

Within one tag clause, values are OR'd. Separate clauses follow the current target's sequential filtering. This illustration uses existing extracted index columns, not undeclared tag fields. EXISTS avoids row multiplication when a note has duplicate tag links.

-- one key with OR'd values, and a negated value in another key:
SELECT n.k0, n.data
FROM notes n
WHERE EXISTS (SELECT 1 FROM note_tags nt JOIN tags t ON t.k0 = nt.i_by_tag_0
              WHERE nt.i_by_note_0 = n.k0
                AND t.i_by_label_0 IN (:tag_a, :tag_b))
  AND NOT EXISTS (SELECT 1 FROM note_tags nt2 JOIN tags t2 ON t2.k0 = nt2.i_by_tag_0
              WHERE nt2.i_by_note_0 = n.k0
                AND t2.i_by_label_0 = :excluded_tag);

Compile negation as NOT EXISTS, not a NOT IN list containing nullable values. Typed tags additionally constrain the tag's type. Preserve prefix-wildcard rules and case behavior per target.

WHERE plus HAVING, and two-stage aggregation

The aggregate pipeline filters observations first, then selects coverage, then buckets and aggregates. packages/wql/src/QueryService.ts:1632-1678. In SQL, fact-level predicates go in WHERE or an inner query; population-level conditions go in HAVING. The query :note{tags:competition} where sum:totalVolume{} > 5000 parses to exactly that split.

-- executable SQLite illustration for an explicitly direct-only population.
-- This is NOT the general detail + substitute-summary WQL plan.
SELECT content_id, SUM(value) AS total
FROM metric_fact
WHERE representation = 'direct'
  AND field_path = :metric_path AND field_kind = :metric_kind
  AND field_dim IS NOT DISTINCT FROM :metric_dim
  AND unit IS NOT DISTINCT FROM :unit
  AND temporal_kind = 'instant'
  AND occurred_at >= :from_ms AND occurred_at < :to_ms
GROUP BY content_id
HAVING SUM(value) > :threshold;

For general queries, SQL filters candidate observations; JS retains conversion, coverage selection and reduction in the first cutover. Do not send a selected set back to the server just to SUM it. Move a complete reduction into SQL only after parity proof. Never SUM detail and overlapping substitute summaries together, average averages without retained weights, use COUNT(events) as COUNT(observations), or apply LIMIT before aggregate selection. Last and delta need recorded order and current tied-endpoint diagnostics. Civil-date membership uses the captured timezone and zoned-noon rule; plain date bounds are not equivalent for arbitrary partial-day windows.

Count before limit, and pagination

List surfaces need the total matched count and one page. The API already computes counts in SQL when a range is representable, ../wod-wiki-api/src/store.rs:311-326. The pattern to standardize:

-- one read snapshot; same predicate binds in both statements.
SELECT COUNT(*) FROM query_block
WHERE data_type = :type;

SELECT occurrence_id, parent_note_id, effective_date
FROM query_block WHERE data_type = :type
ORDER BY effective_date DESC, occurrence_id DESC
LIMIT :page_size OFFSET :offset;
-- keyset next-page predicate, applied to the page statement only:
-- AND (effective_date, occurrence_id) < (:last_date, :last_id)

Offset pages re-scan skipped rows, so keyset pagination is the default for the Library's date windows; offset stays for small jump-to-page needs. Entry search's current union of two independently limited queries cannot be replaced by this without the totalCount decision from finding F8.

CREATE VIRTUAL TABLE block_fts USING fts5(
  occurrence_id UNINDEXED, normalized_text, tokenize='trigram'

SELECT q.occurrence_id, q.parent_note_id

  AND instr(q.normalized_text, :normalized_literal) > 0;

Maintain the FTS rows in the same mutation transaction. Bind a double-quoted FTS phrase with embedded quotes doubled; bind the original JS-normalized literal separately. Use this only after deployed-engine candidate-superset parity checks for strings of at least three Unicode characters. Shorter literals require a scoped scan with the same exact recheck, never an empty-result fallback. PostgreSQL uses pg_trgm on the same normalized text, escaped LIKE patterns and a literal recheck; similarity thresholds must not prune substring matches. JSON payload keys are strings, while FTS rowid is integer, so join the explicit occurrence key, never rowid to UUID.

Capability checks owed before cutover. Verify libsql's tokenizer, literal quote, percent, underscore, backslash, emoji, combining-mark and non-ASCII case parity. Python's SQLite prototype covered only one ASCII term.

Stages and gates

  1. Stage 0, fixtures. Pin current behavior in tests: revision MAX-before-history parity (section 7 code), tag OR/AND algebra per call site, source fence including sourceless rows, wellness pseudo-result reads. The 400-day metric-date fixture gate needs generated civil dates, which the current sample lacks.
  2. Stage 1, minimum read changes. Route selective event and block reads through existing indexes and forward clean-read counts. Gate on row-set parity, all grains, timestamp/civil-date completeness, source fence and ordering. Do not require the entire proposed schema to get this benefit.
  3. Stage 2, projections and write cutover. Back up both engine databases, add typed columns/tables, backfill from retained payloads, reconcile source identities and dedupe links. Install one transaction for source plus projection writes before enabling new reads. Verify identity sets, values, units, temporal evidence, ownership and deletes, not counts alone. If validation fails, leave the old read path active and roll back the migration.
  4. Stage 3, relational read cutover. Compare old and proposed results on fixtures and a real journal. Verify SQL plans, bounded payloads, query count and measured end-to-end latency. Development comparison is temporary; delete it after acceptance. Preserve JSON for rollback and gate projection versions so stale rows cannot silently serve reads. Today's updateEntry, wellness and event projections are separate operations with swallowed or warn-only failures, IndexedDBNotePersistence.ts:170-214; reuse the existing transaction seam, not a new queue.
  5. Stage 4, cleanup cutover. Migrate residual legacy results rows into sessions, then remove the legacy table only when every import, dump and reader path is updated. Never introduce a parallel run table. Static projection cleanup guards (containment rows, occurrence rows) ride the same migration; no cascade touches saved run history.

Rollback. Stages 1 and 2 are reversible by flag because JSON payloads remain the source of truth and projections are derived. A rollback recipe: flag off, derived tables truncated and rebuilt on next enable, no destructive DDL before stage 4. The API migration records its digest in meta, so a downgraded server detects the version gap and refuses silently-broken reads rather than serving stale extracted columns.

check_review.py, runs against the SQLite snapshot 
import sqlite3, sys

db_path = sys.argv[1]  # read-only snapshot copy
db = sqlite3.connect("file:{}?mode=ro".format(db_path), uri=True)
ok = True

def check(label, got, want):
    global ok
    good = got == want
    ok &= good
    print("{}: got {} want {} {}".format(label, got, want, "OK" if good else "MISMATCH"))

# 1. by-type index culls exactly the wod rows the scan would filter
wod = db.execute("SELECT count(*) FROM block_index WHERE i_by_type_0='wod'").fetchone()[0]
check("wod rows via by-type", wod, 2378)
scan = db.execute("SELECT count(*) FROM block_index WHERE json_extract(data,'$.dataType')='wod'").fetchone()[0]
check("wod rows via payload", scan, 2378)

# 2. substring baseline
squat = db.execute("SELECT count(*) FROM block_index "
    "WHERE lower(json_extract(data,'$.rawContent')) LIKE '%squat%'").fetchone()[0]
check("squat matches", squat, 1301)

# 3. source fence page, five rows
fence = db.execute("""SELECT count(*) FROM (
  SELECT data FROM block_index WHERE i_by_type_0='wod'
   AND (json_extract(data,'$.sourceId') IS NULL
        OR json_extract(data,'$.sourceId') IN ('journal','playground','page')
        OR json_extract(data,'$.sourceId') LIKE 'collection:%'
        OR json_extract(data,'$.sourceId') LIKE 'page:%'
        OR json_extract(data,'$.sourceId') LIKE 'guides:%')
  ORDER BY k0 LIMIT 5)""").fetchone()[0]
check("fenced page rows", fence, 5)

# 4. duplicate note_tags pairs
dup = db.execute("SELECT count(*) FROM (SELECT i_by_note_0, i_by_tag_0 "
    "FROM note_tags GROUP BY 1,2 HAVING count(*) > 1)").fetchone()[0]
check("duplicate tag pairs", dup, 10)

# 5. revision order parity, in-memory: MAX(version) must run before the
# history filter, or a superseded revision resurrects.
mem = sqlite3.connect(":memory:")
mem.execute("CREATE TABLE seg (id TEXT, ver INT, is_history INT)")
mem.executemany("INSERT INTO seg VALUES (?,?,?)", [("s", 1, 0), ("s", 2, 1)])
wrong = mem.execute("SELECT count(*) FROM seg WHERE is_history=0 "
    "AND ver = (SELECT MAX(ver) FROM seg WHERE is_history=0 AND id='s')").fetchone()[0]
right = mem.execute("SELECT count(*) FROM (SELECT MAX(ver) AS v FROM seg WHERE id='s') m "
    "JOIN seg s ON s.id='s' AND s.ver=m.v WHERE COALESCE(s.is_history,0)=0").fetchone()[0]
check("filter-first resurrects (buggy shape)", wrong, 1)
check("max-first resolves to none (correct shape)", right, 0)

mem.close()
db.close()
assert ok, "Snapshot differs from reviewed evidence"
print("ALL OK")

Limits of this evidence

  • All timings are warm local medians over a file snapshot. They support structural conclusions, which rows and indexes move data, not latency promises for any product surface.
  • The snapshot predates the vendor schema: no by-user columns, some missing indexes, 19 main stores plus the metric-date junction versus 20 current definitions. Absolute byte totals will differ on current data.

  • The ApiStorage observation instrumented a real client adapter against fixtures; it demonstrates the request shape, not server performance.
  • No benchmark of a proposed table, query or index was run against this snapshot except the fence and trigram prototypes quoted above; every other proposed shape is labeled a proposal.
