Why casting to the TV stalls on the spinner — and what fixes it

Diagnosed 2026-10-07 on “Laboratory TV” (Google TV, Cast build 3.72.446070) via Chrome remote debugging · all findings verified live, not hypothesized.

TL;DR

The published receiver page crashes before React mounts: the TV’s embedded Chrome 92 throws SyntaxError: Unexpected token '{' on a class static {} block inside vendor-Dw7K5vus.js (from @radix-ui/react-collection). The app never boots, so Cast kills it after 60 s (CastInitTimeout) and the spinner never leaves. The production deploy is missing the receiver-specific build that already exists in the repo. A second, independent bug keeps the sender’s Cast button permanently stuck on “Connecting…” after any failure.

The symptom

Casting from wod.wiki to the TV shows our own boot spinner (“Wod.Wiki is prepping the workout…”) forever. On the sender side the Cast button pulses Connecting…, then fails with session_error — and stays disabled even for the next attempt.

The full failure chain

  1. Sender LAUNCHes app 38F01E0E; the TV loads https://wod.wiki/receiver-rpc.html (page load itself succeeds, ~2 s to first paint).
  2. The browser parses /assets/vendor-Dw7K5vus.js line 131 and throws SyntaxError: Unexpected token '{' — an ES2022 class static block the TV’s Chrome 92 cannot parse.
  3. React never mounts. #root stays empty; castContext.start() never runs, so Cast core never sees the app reach RUNNING.
  4. After 60 s Cast core aborts the app: APP_ERROR_TIMEOUT / CastInitTimeout.
  5. The sender’s requestSession() rejects with session_error. The backend left itself in connecting and never resets → the Cast button is bricked until page reload.
  6. The HTML shell’s spinner has no independent timeout, so it spins forever on both ends.

Root cause #1 — the TV runs Chrome 92, the bundle targets a newer browser

Verified live over the remote debugger. The receiver’s user agent on the TV:

Mozilla/5.0 (Linux; Android 14.0; Build/UTTC.250917.004) AppleWebKit/537.36
(KHTML, like Gecko) Chrome/92.0.4515.0 Safari/537.36 CrKey/1.56.500000 DeviceType/AndroidTV

The exact throw, captured via CDP Runtime.exceptionThrown on the device:

url:      https://wod.wiki/assets/vendor-Dw7K5vus.js
line/col: 131:51729
error:    SyntaxError: Unexpected token '{'

Sourcemap lookup pins it to @radix-ui/react-collection’s OrderedDict:

// vendor-Dw7K5vus.js, generated line 131
var QX = new WeakMap,
    $X = class e extends Map {
        static { XX(this, `OrderedDict`) }   // ← Chrome 92: SyntaxError
        #e;
        ...

Class static initialization blocks ship in Chrome 94. The same published page was re-run in a local headless Chrome 92 and reproduced the identical exception at the identical position — the TV hardware is not a factor.

Why the bundle is wrong in the first place

The live page is built by the main playground pipeline (apps/playground/vite.config.ts, which pulls the whole app — CodeMirror, recharts, router — into vendor-*.js and applies no legacy JS lowering). The repo already contains a purpose-built receiver pipeline, apps/playground/vite.receiver.config.ts, which emits assets/receiver-* chunks and lowers legacy CSS — but only the PR preview workflow runs it. The production workflow (main.yml) publishes the artifact from build:app alone, so production has never shipped the real receiver build. Tell-tale proof: the live page still carries the literal dev placeholder G-PROD-ID in its analytics snippet.

Root cause #2 — the sender’s Cast button never recovers

Independent of the TV, ChromecastBackend.startSession() (apps/playground/src/services/cast/adapters/ChromecastBackend.ts) sets state connecting, then awaits two fallible calls with no recovery:

this.setState('connecting');
...
await ChromecastSdk.requestSession();   // throws 'session_error' — uncaught
...
await transport.connect();              // 15 s timeout — also uncaught

Two aggravators make it permanent:

  • The SDK-state subscription deliberately ignores events while connecting or session-active, so CAF’s own NO_SESSION / SESSION_ENDED recovery signals are dropped (lines 85–87).
  • CastButtonRpc disables the button whenever the backend is connecting, and its catch block only logs.

Live evidence from the published sender: castState=NOT_CONNECTED, sessionState=NO_SESSION, both Cast buttons disabled titled “Connecting…”, console showing repeated [CastButtonRpc] Cast failed: session_error.

Why the spinner specifically never gives up

The boot fallback that dismisses #initial-loader is armed after castContext.start() inside the React effect (app/receiver-rpc.tsx). A module-level syntax crash means that code never executes; the ReceiverErrorBoundary renders an error card but the loader overlay (z-index: 99999) sits on top of it. Net effect: any pre-boot failure looks identical to “still loading”.

Appendix: how we saw inside the TV

For next time — this is the working recipe for remote-debugging the receiver on this TV:

  1. In TV settings, enable developer mode, then open Settings → System → Cast and register the Cast software serial (format OR…_ACQZ, distinct from the hardware serial) in the Cast SDK Developer Console. Wait ~15 min, then power-cycle the TV.
  2. The debugger listens on an abstract Unix socket, not TCP: 
    adb connect 10.1.0.94:5555
adb forward tcp:9225 localabstract:cast_shell_devtools_remote
curl http://127.0.0.1:9225/json/list    # page target + inspector URL
  3. Launch the receiver without the (brickable) sender UI, e.g. via pychromecast start_app('38F01E0E', force_launch=True).
  4. Open the DevTools frontend at http://127.0.0.1:9225/devtools/inspector.html?ws=127.0.0.1:9225/devtools/page/<id>. If the auto-generated frontend (hosted on chrome-devtools-frontend.appspot.com) renders blank for the old engine, open the same ?ws= URL through any local modern Chrome’s own /devtools/inspector.html — that worked first try.

The fix, in three steps

1Ship the real receiver build, targeting Chrome 92

  • Add build.target: 'chrome92' (esbuild transpiles static {}, ??.=, private members) to vite.receiver.config.ts.
  • Add the PR workflow’s “Build receiver” step (vite build --config vite.receiver.config.ts) to main.yml so production merges the receiver build into dist/ before the S3/Pages sync — same as previews already do.
  • Expect some runtime-API gaps syntax-lowering can’t fix (Object.hasOwn, Array.prototype.at, Promise.withResolvers all appear in current vendor code); add explicit core-js polyfills behind the receiver entry if the Chrome 92 smoke run flags them.

2Make both ends fail loudly and recover

  • ChromecastBackend.startSession(): wrap requestSession() + transport.connect() in try/catch; on failure dispose the half-built transport and setState('ready'). Stop suppressing CAF NO_SESSION/SESSION_ENDED while connecting.
  • Dismiss #initial-loader from the HTML shell itself (inline window.onerror hook + a shell-level timeout), so no bundle-level crash can ever produce an infinite spinner; have ReceiverErrorBoundary dismiss it too.

3Verify on the engine that broke it, then the real TV

  • Automated: serve the built dist/, load receiver-rpc.html in headless Chrome 92, assert no SyntaxError, #root populated, loader dismissed.
  • On-device: cast to Laboratory TV; confirm App started … RUNNING in logcat -s cast_shell, workout renders, timer sync works; then exercise cancel-and-retry to prove the sender button recovers.
