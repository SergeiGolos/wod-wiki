WHITEBOARD CONCEPT

The 4-Part Mental Model + Reactive Page Datasets

Every WQL query follows one uniform sequence: WHAT{WHICH} WHEN by {GROUP} | SHAPE. Today, dashboard widgets repeat the full query string 6 to 10 times, forcing multiple full scans across SQLite/telemetry facts. With the Stored Source (=> @source) operator, a page extracts a bounded dataset once, and every downstream chart performs instant micro-aggregates.

1. WQL Find Logic Crosswalk Matrix

WQL exposes six distinct discovery nouns under the find: head. The noun directly dictates the grain, result shape, supported dimensions, and default time anchors:

Noun / Head Output Grain & Shape Supported Filter Keys Grouping Dimensions Time Anchor Pipes & Units Canonical Example
find:note List of Markdown note cards (Cards / Feed) source, type, intent, format, category, tags, frontmatter keys by {tag}, by {source}, by {category}, by {format} Note date (falls back to createdAt) | order by title | limit N find:note{source:journal, tags:benchmark} last 4w
find:block Parsed workout block cards (WODs, EMOMs, intervals) effort, format, discipline, intensity, origin by {format}, by {discipline}, by {effort} Parent Note date | limit N find:block{effort:thruster, format:amrap} last 8w | limit 20
find:effort Registry items from movement catalog discipline, intensity, category, plane by {discipline}, by {intensity} N/A (Registry catalog) | order by name find:effort{discipline:strength, intensity:high}
find:session Grouped run cards (1 per result execution) result, note, plane, discipline, source by {week}, by {discipline}, by {plane} completedAt (falls back to startedAt) | order by date desc | limit N find:session{plane:load} last 4w
find:segment Flat tabular rows at movement/segment grain effort, discipline, intensity, plane, origin by {effort}, by {week}, by {day} Recorded metricDate in kg|lb, | select ... | order by ... | limit N find:segment{effort:snatch} last 12w in kg | select date, totalVolume
find:event Granular raw telemetry fact events effort, discipline, metric, origin by {day}, by {effort} Recorded metricDate | limit N find:event{effort:back-squat} last 7d | limit 100
Content Discovery (Notes & Blocks) Lists

Searches authored markdown documents and block content hashes. Grouping produces visual shelves (e.g. grouped by tag or format) in stream and collection views.

Session Runs (Planes) Run Cards

Replaces old rows:all and rows:<plane> heads. Grouped by result session ID, showing segment cards, load distributions, and system metadata.

Telemetry Tables (Segment & Event) Tabular

Cross-workout flat data table. Accepts column projection with | select, unit conversion with in kg|lb, and sorting with | order by.

2. Properties for Grouping (by {...})

Grouping partitions results into distinct shelves (for lists/tables) or distinct series / bar clusters (for numeric charts). Multiple dimensions can be chained hierarchically.

Dimension Family Keywords / Values Granularity & Alignment Effect on Lists (find:*) Effect on Charts (agg:*)
Civil Time Buckets day, week, month, quarter, year Local timezone: day is 00:00–23:59; week is strictly Monday–Sunday civil week. Splits items into time sections (e.g. "This Week", "Last Week"). Buckets X-axis timestamps into discrete bars or data points.
Workout Structure session, round, block Execution grain: session = discrete workout; round = interval/set; block = WOD section. Groups blocks/cards by session. Splits series per session or round (e.g. pacing across rounds).
Movement Taxonomy effort, discipline, intensity effort = movement slug; discipline = strength / gymnastics; intensity = low / mod / high. Shelves by movement or sport discipline. Creates multi-line series or stacked bars by category.
Provenance & Source source, origin, plane Where the item lives (journal, collections) or who generated it (user, runtime). Groups cards by catalog or journal origin. Segments telemetry by system plane or user input.
Authored Tags & Metadata tag, coach, format, equipment Any custom tag or frontmatter attribute assigned to notes/blocks. Shelves items by author or equipment. Slices volume by custom coaching tag.

Hierarchical Multi-Dimension Grouping

When multiple dimensions are specified, outer dimensions group first, followed by nested sub-dimensions:

sum:sessionLoad{} by {intensity, week}
// Splits first by intensity tier (high/mod/low), then buckets weekly on civil Mondays

sum:tis{} by {session, day}
// Groups by civil day on X-axis, with stacked/clustered bars per session

find:note{source:collections} by {discipline, format}
// Shelves collection notes into Discipline headers, then sub-shelves by workout format (EMOM/AMRAP)
Rule on .rollup() vs by {week}:

Single-unit rollups like .rollup(1w) and .rollup(1d) are obsolete and prohibited; write by {week} (civil Monday) or by {day} instead. Rollups are preserved strictly for multi-unit smoothing, such as .rollup(2w) (bi-weekly buckets) or .rollup(4w) (4-week rolling blocks).

4. Date Range Selection Variants & Time Anchors

Time clauses restrict queries along the temporal axis. WQL supports rolling relative windows, civil calendar spans, and preset macro anchors.

Variant Type Syntax Pattern Semantics & Resolution Example
Rolling Relative last <N><unit> d (days), w (weeks), m (months), y (years), h (hours).
Calculated dynamically from current clock timestamp backwards. 		last 4w (last 28 days)
last 90d (rolling quarter)
last 48h (recent telemetry)
Closed Civil Range from YYYY-MM-DD to YYYY-MM-DD Inclusive bounds matching local calendar days from start 00:00 to end 23:59:59. from 2026-01-01 to 2026-03-31
Open Civil Range from YYYY-MM-DD From specified starting date up to the current live moment. from 2026-09-01
Calendar Macros (Proposed) this week, this month, ytd Aligns to current calendar milestone (e.g. Monday midnight for this week, Jan 1 for ytd). sum:totalVolume{} this month by {week}

The Unified "When It Happened" Invariant

Historical versions of WQL suffered from time-anchor divergence (e.g. back-dated journal notes filtering on createdAt while telemetry facts filtered on metricDate). Under the unified model, all nouns filter on when the training actually occurred:

find:note

Note Date

Evaluates note frontmatter date. Falls back to createdAt only if backdate metadata is absent.

find:session

Completion Timestamp

Evaluates session completedAt. Falls back to startedAt for aborted/in-progress runs.

Telemetry (agg & segment)

Metric Date

Evaluates recorded metricDate timestamp emitted by the workout clock/sensor.

5. The New => @source Stored Source Operator

NEW CAPABILITY · PAGE DATASETS

Dashboard pages and complex review notes often contain 5 to 10 widgets examining the same cohort of workouts over the same time window. Today, each widget independently repeats the same filters, date clauses, and join predicates. This leads to code duplication, fragile updates, and redundant SQLite/fact scans.

The => @sourceName operator binds the output of any discovery query to a named in-memory page source on the current page:

// 1. Declare once at top of dashboard or note
find:segment{effort:snatch|clean*, intensity:high} last 12w => @olyLifts

// 2. Downstream widgets query directly against @olyLifts:
@olyLifts | sum:totalVolume by {week}
@olyLifts | max:resistance by {week}
@olyLifts | avg:pace by {effort}
@olyLifts | select date, effort, totalVolume | order by date desc | limit 5
How It Works in Page Lifecycle Execution Model
  • Single Evaluation: The query engine runs find:segment once upon page load.
  • Reactive Cache: The result is registered in PageSourceRegistry under the key @olyLifts.
  • Zero DB Scans Downstream: Downstream widgets do not touch SQLite; they compute in-memory aggregations and projections directly against @olyLifts in microseconds.
  • Reactive Cascade: If the user changes a date range or filter on @olyLifts, all 5 subscriber charts update instantly in lockstep.
Stored Source Contract Interface
  • Identifier Syntax: Starts with @ followed by alphanumeric/kebab-case identifier (e.g. @olyLifts, @benchmarks, @recentRuns).
  • Scope: Page-local (lives within the current dashboard / note session).
  • Result Shape: Stores typed tabular rows (find:segment, find:event) or grouped runs (find:session) or card entities (find:note).
  • Secondary Slicing: Downstream queries can apply further sub-filters: @olyLifts | sum:totalVolume{effort:snatch} by {week}.

6. How Aggregate Operations Become Simpler to Reason About

Once data sets can be stored into @source, the syntax of aggregate operations collapses from repetitive database queries down to pure mathematical reductions over a known table.

Syntax Variant Grammar Pattern Ergonomic Advantage Ideal Usage
Pipeline Pipe (Recommended) @source | <agg>:<metric> by {<dims>} Reads naturally left-to-right: "Take dataset @source, pipe into volume sum grouped by week". Interactive query blocks, dashboard widgets, CLI workbench.
Arrow Flow @source => <agg>:<metric> by {<dims>} Uses the same arrow symbol for chaining: Source produces dataset ➔ flows into aggregate reducer. Notebook pipelines, multi-step metric transformations.
Preposition Directive <agg>:<metric> in @source by {<dims>} Reuses familiar SQL/WQL preposition in. Single-metric callouts, embedded inline telemetry chips.
Widget Block Attribute ```query:timeseries(source=@source) Cleanest markdown fence: query body contains only the bare metric and grouping. Dashboard markdown files.

Why Downstream Queries Are Vastly Simpler

1. Zero Date / Filter Noise

No need to re-type last 12w, effort:snatch|clean*, or intensity:high across 6 widgets. The source defines the bounded cohort once.

2. Pre-baked Relational Joins

Complex cross-store joins (e.g. where find:note{format:emom}) execute once when populating @source. Downstream queries don't need to join again.

3. Instant Client-Side Slicing

Downstream charts can perform micro-slices with near-zero latency: @olyLifts | sum:volume{effort:snatch} by {week} filters the in-memory array in <1ms.
