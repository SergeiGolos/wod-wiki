Review + design proposal · 30 September 2026

One query language.
One interaction contract.
Two input layouts.

The shared composer exists. Its surrounding controls and its own pickers still behave like different editors. Fix query preservation first, then unify selection rules without forcing a desktop command bar onto a phone.

Reviewed source at 29d85a47, recent interaction commits, and the running local app. This document proposes changes only. No application code was changed.

Recommendation

Choose option A: an adaptive token composer.

Keep readable query chips, use one searchable picker for adding and editing clauses, restore native Tab navigation, and put the same choices in a bottom sheet on touch devices. Keep a lossless text editor available for WQL the guided controls cannot express.

This is the smallest useful cutover because it retains WqlComposer, its parser/serializer, the inline value editor, and the existing host entry points. The stream header should become a compact presentation of that editor, not a second place with different parsing and deletion rules.

Unify the query and selection behavior. Do not unify away the difference between searching, running analytics, and saving a note or dashboard widget.

Resolve the two correctness gaps before polishing navigation.

Find-query suffixes disappear in the pill round-trip. The new noun-based source choices also disagree with the old source-plane allowlists. A nicer picker on top of these gaps would make the wrong behavior easier to reach.

Confirmed drift, in priority order

P1 · query preservation

Guided editing silently removes find-query suffixes

astToPills accepts a find query but projects only target/source, time, filters and join. The find serializer path emits no grouping, display unit or pipes. The raw-query escape hatch therefore does not protect these valid queries.

Input  find:segment{effort:snatch} by {effort} in lb | limit 5
Output find:segment{effort:snatch}

Observed in a direct source smoke and when pasting into the running palette. In uncontrolled hosts, the initial emission can rewrite the seeded query; in controlled hosts, a later pill edit can remove the omitted clauses. Do not claim a query is guided-editable unless every clause survives.

queryAst.ts:131–168, 283–304; WqlComposer.tsx:223–234, 637–650.

P1 · capability mismatch

The source picker and filter allowlists no longer agree

Options are now singular nouns: Note, Block, Effort, Session, Segment, Event. “Metrics” and journal/collection scopes are absent, although the model still restores them. Effort-specific allowlists still test source === 'efforts', so the new effort choice receives the content filter list instead of discipline/intensity/origin. Segment/event allowlists omit effort despite documented effort-filter examples.

Observed source picker shows six nouns, no selected item for an existing collections query, and no Metrics choice. Direct source smoke confirms the singular-effort allowlist mismatch.

queryClauses.ts:92–140, 189; queryAst.ts:136–147, 179–184; wql-reference.md:48–53, 106.

P2 · keyboard access

Tab changes a visual state instead of moving focus

The composer prevents native Tab and cycles pill bodies/removes while the input retains focus. Reaching either end resets the virtual selection, so another Tab starts the cycle again. This intercepts the route to Run, Apply, add controls and later widget fields. Alt+Tab is also treated as backwards navigation even though operating systems own it.

Observed after repeated Tab on the desktop explorer: document.activeElement remains the composer input. Its role, aria-controls and aria-activedescendant are absent. The value list has option roles, but the focused input does not identify the highlighted option.

WqlComposer.tsx:357–377, 556–634, 728–744; QueryPalette.tsx:79–89; InlineClauseEditor.tsx:49–60, 105–120.

P2 · selection consistency

Typing sometimes searches options and sometimes does nothing

Filter-key typeahead uses prefix matching on keys/labels and rejects whitespace or colons. Value pickers use substring matching, except static selects ignore the typed text altogether. Typing eff into Group By or Source leaves the full list unchanged. That behavior was reproduced in the running explorer and palette.

The visible “Search for typed value” row also has no normal keyboard index. Enter picks a matching suggestion first; the typed row is selectable with a pointer while suggestions remain. Make “Use exact text” a first-class option with the same arrow/Enter behavior as every other row.

filterTypeahead.ts:34–48; clauseItems.ts:53–78; WqlComposer.tsx:529–547; InlineClauseEditor.tsx:85–102.

P2 · add versus edit

Three ways to add a clause produce different next steps

Typeahead adds or edits a clause and opens its editor. Filter dropdown excludes existing types, adds a blank clause and does not activate the value editor. Calculation dropdown handles another list of clause types. Group By is single-value in its editor; restored queries can contain several group pills, but Add Calc offers no second Group By once one exists.

Use one clause catalog with “Add” or “Edit” status, and always go straight to the value step. Treat grouping as an ordered multi-selection. Adding a filter should not leave a blank pill the user must find and click again.

WqlComposer.tsx:394–418, 444–455; QueryPalette.tsx:526–563, 613–644; clauseVocab.ts:17–26; queryAst.ts:179–185.

P2 · host action

Enter, Run and Apply do not consume the same draft

Enter commits pending text before a second Enter submits. The explorer's Run button submits host draft state, not necessarily the pending input. Palette Apply uses a separately debounced live query. The block inspector and widget composer have no submit callback for valid raw WQL entered in the free-text path.

Define one current draft, one validity result, and one host commit action. Every Run/Apply path must flush pending input before acting; no debounce race and no second Enter ritual.

WqlComposer.tsx:425–442, 636–657; AnalyticsExplorerPage.tsx:352–365; PaletteShell.tsx:173–177, 214; WqlQueryInspectorModal.tsx:86–92.

P2 · touch usability

The mobile entry is reachable; the editor actions are not

At 390 × 844, the palette sits near the top. Apply is 28px high at y=18; Cancel is 30px high at y=17; pill remove targets are 16 × 16px. The editor autofocuses on mobile. The inline option rows and selected-value remove icons remain desktop-sized.

Use 48px rows and action targets in the lower portion of the viewport. Open selection without summoning the software keyboard. Offer an explicit Search action when typing is useful.

PaletteShell.tsx:194–225; QueryPalette.tsx:113–130; InlineClauseEditor.tsx:64–79, 105–115. Dimensions measured in Chromium; software-keyboard reach was not physically tested.

P2 · grouping precedence

A view setting can appear to work while the query overrides it

The stream chooses grouping from WQL first, then View settings, then its default. Route settings separately configure the available Group-By list and source choices. The composer has its own static grouping and source options, so those configurations do not constrain all editing paths equally.

Expose the winner. When WQL owns grouping, show “Controlled by query” in View settings with an Edit query action, or update WQL through the same grouping picker. Do not offer an apparently active layout choice that the query immediately overrides. Browser-local preferences may choose defaults and favorite options, but must not change which WQL clauses are valid.

QueriableStreamView.tsx:255–262; routeWqlConfig.ts:15–22, 87–94; QueryDefaultsSection.tsx:209–260; queryClauses.ts:133–158. Source-reviewed, not a runtime reproduction.

Three unification options

All three require lossless query handling, one capability catalog and the same selection contract. These are alternative primary editing layouts, not three new components to build and maintain.

A · recommended

Adaptive token composer

Readable chips plus one “Add or edit” picker. Desktop edits values beside the query. Mobile edits the same values in a bottom sheet. Advanced WQL stays available through a text view.

Desktop

  • Native Tab between real controls; arrow navigation inside the open list only.
  • Filter keys, values and grouping all searchable.
  • Chip click/Enter opens the same picker as Add.
  • Text/WQL mode is explicit, not a hidden fallback.

Mobile

  • Compact query summary opens a bottom sheet.
  • Category → field → values, one decision at a time.
  • Selected values remain checked and visible.
  • Sticky Cancel/Apply footer; keyboard stays closed until Search.

Tradeoff

Lowest replacement scope. Still needs a text editor for joins, pipes or clauses without guided controls.

Best fit

Streams, palette, widget editor and query blocks. Explorer keeps its Run action.

What retires

Header-only parsing/deletion rules, virtual Tab ring and separate add/filter/calculation selection logic.

B · text first

WQL command line with a guided touch helper

A real text editor is the primary desktop query editor. Completion follows caret context. A mobile “Build query” sheet inserts or updates the same parsed clauses.

Desktop

  • Type WQL directly with key/value/dimension completion.
  • Arrow/Enter select explicit completion; Tab leaves the editor.
  • Parser errors point to the relevant text; full syntax remains editable.

Mobile

  • Default to guided categories, not a dense code input.
  • “Edit WQL” opens a full-screen text view for experts.
  • Never rewrite unsupported text clauses when using a guided field.

Tradeoff

Best syntax coverage and keyboard speed for experts. Larger completion/editor integration and more learning for occasional users.

Best fit

Explorer and query-block authors. Weaker default for people browsing workouts.

What retires

Pills as the primary editing model. Chips become optional read-only summaries.

C · structured first

A query inspector with named sections

A single form exposes Find/Measure, Filters, Time, Grouping and Presentation. Desktop uses an anchored panel; mobile uses a bottom drawer or full-height sheet.

Desktop

  • Native labelled fields and buttons throughout.
  • One searchable multi-select per field; visible Apply/Run.
  • WQL preview below the form, editable through Advanced.

Mobile

  • Large section rows with counts and current values.
  • Full-width value choices with checkbox/radio semantics.
  • Apply footer stays visible while sections scroll.

Tradeoff

Easiest to discover. More space and more steps than A; slower for repeated keyboard use. Guided controls must not pretend to cover every valid WQL expression.

Best fit

Widget configuration and mobile browsing, where discoverability matters more than compactness.

What retires

The always-editable chip bar. Headers show a summary and an Edit query button.

Typeahead needs an explicit choice

Type “eff”→Search text “eff” + Effort filter→↓ choose Effort→Enter opens values→Type “squat”

List “Search text” and “Use exact value” alongside completions when relevant. Every displayed selectable row gets an index, an accessible name and a keyboard path. Filter key matching may prioritize prefixes; value matching may use substrings. Both must actually narrow the list.

Keep one active list at a time. In the palette, provide a named Results region and an explicit way to focus it. Announce “Effort options” versus “Search results”; do not rely on a faint highlight to explain what Enter will do.

Focus and screen-reader requirements
  • Label the query input. For input-owned selection, use a combobox with aria-expanded, aria-controls, stable option IDs and aria-activedescendant. For chip navigation, move real focus between semantic buttons.
  • Use a managed dialog with focus containment and focus restoration. The inspector's current aria-modal declaration alone is not focus management.
  • Use checkbox semantics for independent multi-selection, radio semantics for a single choice. Keep action buttons outside a listbox's options.
  • Announce validity, changed selection and preview/result counts politely. Errors name the clause and corrective action.
  • Visible focus must identify the actual active control; do not remove the input outline without a replacement.

Mobile proposal for thumb selection

Do not shrink the desktop composer. Keep the query summary compact and move editing into a reachable sheet. Use at least 44 × 44px targets; propose 48px rows and footer actions. Support both hands without a right-only action cluster.

Selection without typing

  1. Tap “Filters · 2” near the bottom navigation/toolbar.
  2. Sheet opens with current query summary and large categories.
  3. Tap Effort, then check Back squat and Front squat.
  4. Tap Done to return to the query sheet.
  5. Tap Apply query in the sticky footer.

Selected values remain checked; multi-select stays open. Single-select returns to the previous sheet after selection. “Done” ends a field edit; “Apply query” commits the host draft. Those are different actions.

When typing helps

Tap Search within the field picker to focus a 16px-or-larger input. The option list and footer resize with the visual viewport. No input autofocus on initial sheet open. External keyboards still use the desktop key contract.

Layout rules

  • Footer respects env(safe-area-inset-bottom); no action sits behind the keyboard or browser chrome.
  • Sheet body scrolls independently with contained overscroll. Selected values and action footer remain visible.
  • Back and Cancel have tap targets. Swipe dismissal is optional, never the only exit.
  • Clear/remove lives on a full-size row or action, not a tiny × inside a chip.
  • Use native date inputs for explicit ranges. Treat “last 4w” as four weeks, not a calendar month.

Every commit uses the same resolved draft as the visible query. Validate after resolving pending input. Do not run the previous query because the last 150ms of typing have not emitted yet.

Smallest coherent cutover sequence
  1. Make projection lossless or reject unsupported guided queries into text mode. Correct singular noun allowlists and split noun/source/kind selection.
  2. Replace virtual Tab navigation with real focus and one active picker contract. Make all closed lists searchable; make exact-text rows keyboard-selectable.
  3. Use the same clause catalog for Add, edit and completion. Add ordered grouping selection and preserve every untouched suffix.
  4. Make the stream header reuse that entry behavior. Standardize draft resolution before Run/Apply/Save.
  5. Adapt the existing dialog host to a bottom sheet for touch selection. Keep host-specific footer labels and persistence boundaries.

No app implementation is included in this review. Option A should be one cutover with shared behaviors, not old/new editors maintained indefinitely.

Configuration is not another query engine

Settings saves defaults, not the current page draft. Keep browser-local source/group favorites distinct from query validity. Provide the shared picker as an optional helper, preserve direct WQL text editing, and validate configured option values against current noun/source/dimension capabilities. Reset affects configuration only.

Acceptance scenarios for the chosen design

These are proposed checks for future implementation, not tests claimed to pass today.

  1. Lossless edit. Open find:segment{effort:snatch} by {effort} in lb | limit 5, change time, and verify grouping, unit and limit survive in the emitted query and saved fence.
  2. No Tab trap. From input, Tab/Shift+Tab reach chips, Add, Run/Apply, widget fields and the next page control. Focus and assistive output agree.
  3. Same typeahead everywhere. Enter the same filter through stream header, palette, explorer, widget and block inspector. Same choices and WQL meaning; only final host action differs.
  4. Plain text stays plain. Type a word that matches a filter key. Enter searches text unless the user explicitly selects the filter.
  5. Exact value is reachable. With both partial suggestions and an exact-text row visible, arrow to either and select it. Pointer and keyboard choose the same value.
  6. Multiple groups. Add week and effort, remove one, reorder them without drag, reopen and verify both order and semantics.
  7. Capabilities agree. Find Effort offers discipline/intensity/origin; segment/event offer their supported filters; switching kind is explicit; source scope remains separate.
  8. No stale action. Type or paste then immediately Run/Apply without waiting for debounce. The executed/saved query equals the visible draft.
  9. Correct Escape ownership. Close a field picker without dismissing its host; close host next; return to opener. Enter never both toggles a value and opens a result.
  10. Thumb flow. At 320px and 390px widths, complete filtering/grouping without opening a keyboard. All targets meet the touch size; footer remains above safe area and real software keyboard.
  11. Cancel is safe. Cancel stream editing, widget editing or query-block editing and verify original page query, dashboard or note source is unchanged.
  12. Advanced syntax survives. Negation, prefix, dynamic tags, civil ranges and joins either have correct guided controls or stay editable as original WQL. Never silently simplify them.
