WQL Simplification Walkthrough

Status: implemented (tickets #1041–#1051, 2026-09-30). Companion to wql-inventory.html. It proposes five changes that cut the number of concepts you need to hold in your head, and every current capability still has a way to be expressed. Each change comes with a before/after, the evidence behind it, and how it affects the library streams and dashboards.

Evidence comes from packages/wql/src/QueryService.ts, wql.ts, wqlSuffix.ts, vocabulary.ts, apps/playground/app/views/stream/streamProfile.ts, markdown/dashboards/*.md, and from running parseQuery directly on the queries shown.

1. The new mental model

Every query answers four questions, in the same order every time:

WHAT{WHICH} WHEN by {GROUP} | SHAPE
SlotQuestionValues
WHATDo I want things or numbers? Things: find:note · find:block · find:effort · find:session · find:segment · find:event
Numbers: sum|avg|min|max|count|last|delta:<metric> (unchanged)
WHICHWhich ones?The {key:value} filters stay as they are: , AND · | OR · ! NOT · * prefix · "quoted"
WHENOver what period?last 8w · from … to …
GROUPSplit how?by {week} · by {effort, discipline} · by {tag}
SHAPETrim or order the output?| select … · | order by … · | limit N · in kg

Joins keep the single word where, and they read the same way in both directions: the right-hand side is always the other kind.

sum:totalVolume{} where find:note{format:emom}          numbers, restricted to these things
find:note{intent:benchmark} where sum:totalVolume{} > 5000   things, restricted by a number

2. Change 1: fold rows: into find: nouns

rows: has 13 targets, and 5 of them are redundant. ROWS_CONTENT_PLANES (QueryService.ts:78, 592) makes rows:note, rows:block, rows:effort and rows:page behave exactly like rows:all. The other 8 targets are output-type filters written as heads. Separately, rows:segment returns a runs view when it has a scope key and a flat table when it doesn't (runRows, lines 558–563), so the same head gives two different result shapes.

rows:all{result:r1}                  runs, every plane
rows:segment{result:r1}              runs, segment plane only
rows:load{result:r1}                 runs, load plane only
rows:note{note:n1}                   same as rows:all{note:n1}
rows:segment{effort:snatch}          FLAT TABLE (no scope → other mode)
rows:all{} last 4w                   ✗ parse error: needs a scope
find:session{result:r1}              runs, every plane
find:session{result:r1, plane:segment}
find:session{result:r1, plane:load}
find:session{note:n1}
find:segment{effort:snatch}          always a flat table
find:session{} last 4w               list of sessions in window

Rule: the noun decides the result shape. session gives grouped run cards (RowsQueryResult.runs). segment and event give a flat table (RowsTableData). The output plane becomes an ordinary filter key, plane:, with the same values as KNOWN_OUTPUT_TYPES.

TodayAfterFunctionality kept
rows:all{scope}find:session{scope}Identical.
rows:<plane>{scope} (8 planes)find:session{scope, plane:<plane>}Identical. Also gains plane:load|system (OR) and !plane:compiler.
rows:note|block|effort|page{scope}find:session{scope}Identical; these heads were aliases.

Implementation: in wql.ts, map the new heads onto the existing ParsedRowsQuery, with outputType taken from plane:. runRows dispatches on the noun instead of on whether a scope key is present. WQL_ROWS_TARGETS goes away. The UI's isRowsQuery check becomes a noun check.

3. Change 2: one key for "where it lives"

Today the same idea has three spellings, and the aliases disagree at the edges:

  • WQL_SOURCE_VALUES has 8 values. page and pages are the same value, and all means "leave the filter out".
  • find:page is not its own plane. It runs the isPage heuristic over the notes store (QueryService.ts:760–768), and it has 0 uses in the repo.
  • The composer's WQL_SOURCES heads (notes, blocks, efforts, metrics, …) add a third vocabulary on top.
find:page{}
find:note{source:page}
find:note{source:pages}
find:note{source:all}
find:note{source:page,type:collection}
find:note{source:guides}             (+ type: to narrow)
find:note{source:guides}
find:note{source:guides}
find:note{}
find:note{source:collections}

Rule: source: accepts exactly journal | collections | feeds | guides | playground. Page-ness is handled by type:. The composer chips show the six nouns from §1 and nothing else.

Decision needed: the ADR (Note-Page-WQL-Alignment, Option B) calls for a real page table. If that is still the plan, bring find:page back when the table exists, with join semantics. Keeping a heuristic alias with zero callers only hides the gap.

4. Change 3: one way to bucket time

.rollup(1w) does nothing when by {week} is present. QueryService.ts:1082 sets rollupMs = timeDim ? null : …. The idiom by {week}.rollup(1w) still appears 31 times, so readers keep assuming it matters.

A bare .rollup(1w) is also a trap. It buckets by Math.floor(timestamp / 7d) from the Unix epoch, and 1970-01-01 was a Thursday, so those "weeks" run Thursday to Wednesday UTC. by {week} uses civil Mondays in the user's timezone.

sum:totalVolume{} by {week}.rollup(1w)   rollup ignored
sum:totalVolume{} .rollup(1w)             Thu–Wed UTC weeks
sum:totalVolume{} by {week}               Mon–Sun civil weeks
sum:tis{} by {session}.rollup(1d)         per session per day
sum:totalVolume{} by {week}
sum:totalVolume{} by {week}               (one meaning)
sum:totalVolume{} by {week}
sum:tis{} by {session, day}

Rule: time buckets are ordinary by dimensions (day, week). .rollup(N) stays only for widths that aren't 1, such as .rollup(2w) for fortnightly bars, and those are aligned to civil Mondays. 1d and 1w become parse errors that point to by {day} and by {week}.

Functionality kept: every current output can still be produced. The Thursday-aligned epoch weeks are the one exception, and I found nothing that depends on them.

6. Change 5: one time-anchor rule

last 4w means different things depending on the head. On notes and blocks it filters on createdAt (QueryService.ts:854–856). On facts it filters on the recorded metricDate. A back-dated journal entry for 2026-09-01 that was typed today therefore shows up in find:note{} last 1w, while its metrics don't show up in sum:reps{} last 1w.

find:note{source:journal} last 1w     by createdAt
sum:reps{} last 1w                     by metricDate
find:note{source:journal} last 1w     by the note's date
sum:reps{} last 1w                     by metricDate

Rule: the window always filters on when it happened. For a note that's its date, falling back to createdAt. For a session it's completedAt. For a fact it's metricDate.

Decision needed: this changes which notes appear on /journal for back-dated entries. It's the only change here that visibly alters existing results. If createdAt is intentional (for example, a "recently touched" view), keep it and put the rule in the composer tooltip instead.

    Cross-workout snatch table. Same as today's rows:segment, with a noun that says what it is.

    Sessions that logged wellness output. Can't be expressed today.

8. Applied to dashboards

Dashboards use the numbers family almost exclusively, so for them the change is mostly deleting noise. Here is markdown/dashboards/training-block-review.md:

```query:timeseries-2
sum:totalVolume{} by {week}.rollup(1w)
```
```query:timeseries
avg:tis{} by {week}.rollup(1w)
```
```query:stacked-bar
sum:sessionLoad{} by {intensity}.rollup(1w)
```
```query:timeseries
sum:sessionLoad{} by {week}.rollup(1w)
```
```query:timeseries-2
sum:totalVolume{} by {week}
```
```query:timeseries
avg:tis{} by {week}
```
```query:stacked-bar
sum:sessionLoad{} by {intensity, week}
```

```query:timeseries
sum:sessionLoad{} by {week}
```

The third widget is the interesting one. Today by {intensity}.rollup(1w) produces Thursday-aligned UTC weeks per intensity. by {intensity, week} produces civil Monday weeks, which match the by {week} charts beside it. After the change, every bar on the board lines up on the same week boundaries.

From benchmark-pr-board.md:

last:elapsed{effort:fran} by {week}.rollup(1w)

last:elapsed{effort:fran} by {week}
sum:tis{} by {session, day}

Widget rule

Today DashboardView and LanguageWorkbench reject any find or rows query in a widget with a generic error. With two kinds, the rule fits in one sentence: chart and value widgets take numbers; table and list widgets take things. The rejection message can then say which widget type to use.

```query:table
find:segment{effort:fran} last 26w | select date, elapsed | order by elapsed | limit 5
```
    Top-5 Fran times as a table widget. Optional: only worth adding if a dashboard needs it.

9. Bugs found while grounding this

/sessions default query doesn't parse. parseQuery('rows:all{} last 4w') returns "Rows query needs a scope: result:, block:, note:.", and wql.test.ts:450 asserts this behavior. streamProfile.ts:156 uses it as the page default, and the recent-sessions menu uses rows:all{} last 2w. Per entrySearch.ts:15, invalid WQL resolves to an empty list, so [INFERENCE] /sessions always shows its empty message.
/session/:date default query doesn't parse. rows:all{date:2026-09-17} returns "Unsupported rows filter(s): date." (from streamProfile.ts:196).

Both are symptoms of Change 1: there's no head for "list sessions". find:session{} last 4w fixes them as part of the model rather than as a special case.
