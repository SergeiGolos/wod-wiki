# Typed notes: wayfinder review and Playground impact

Review of [Typed Notes, Segments & Mode-Aware Widgets](https://github.com/SergeiGolos/wod-wiki/issues/1025).

[Published review overview](https://github.com/SergeiGolos/wod-wiki/issues/1025#issuecomment-5705519988) — recommendations only; the map's decisions remain unchanged.

Datatype-by-datatype working proposals and inline feedback questions now live in the [domain-model review guide](../domain-model/todo.md#datatype-review-guide). That guide assigns each question a document owner; neither the drafts nor this review close the Wayfinder decisions.

**Verdict: unify the content contract and reusable components—not every storage record, page layout, or interaction.** The direction is sound. The current map makes the route harder by combining types, permissions, rendering, indexing, and migration into one taxonomy exercise. Its highest-risk missing question is how a composed page edits the correct note without losing source or history.

This is a review and proposed simplification, **not a resolution of the open decisions**. No application code, schemas, route behavior, or ticket statuses change here. Library/listing routes remain out of scope. Source facts below refer to the working copy inspected on 2026-09-16; proposed behavior is explicitly a recommendation.

## 1. Keep the useful distinctions; remove the accidental ones

| Concept              | Recommended responsibility                                                                                                                            | What it should not become                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Note**             | The authored content unit: identity, type descriptor, metadata, ordered segments. Efforts are already markdown-authored notes in the domain.          | A new superclass hierarchy, or a requirement that every entity use the same database table.                      |
| **Page**             | A presentation/composition of one or more notes, with explicit configuration and note ownership preserved. Configuration can itself be note-authored. | Another copy of every note's content, or a giant concatenated editable string with implicit ownership.           |
| **Note type**        | An explicit descriptor selecting relevant configuration, validation, and default presentation. Keep `note` as the ordinary default.                   | A compound value encoding ownership, journal placement, mobile layout, permission, and every widget combination. |
| **Segment**          | An ordered piece of authored content, recognized from source; a widget presents it or edits that source.                                              | A separate persisted entity kind for every graph style, heading level, breakpoint, or overlay.                   |
| **Widget**           | A reusable rendering/interaction component for a segment. Query charts are presentation variants of query content.                                    | A page-aware mini-application that opens storage, parses routes, or creates its own runtime.                     |
| **Tags and queries** | Classification and discovery. A WQL segment displays matching notes; a note can appear in several query results.                                      | Authoritative ownership, permission, or a second writable membership list kept in sync with query results.       |
| **Projections**      | Effort metadata and content-search indexes derived from authored content where needed.                                                                | A second independently editable source of truth.                                                                 |

These are responsibilities, not seven new interfaces or tables. Keep the existing storage representation until a concrete requirement forces a change. Today `Note` is already slim and reconstructs its content from versioned segments [S1]. Do not add another independently writable `Note.rawContent` alongside them.

**Simpler composition:** a route host supplies note content, allowed actions, and existing query/runtime collaborators; page layout composes shared segment presentations; the CodeMirror adapter translates source edits. The widget does not need to know whether its host is a journal, effort, or syntax page.

## 2. Where the map overcomplicates the model

| Current assumption                                                                                                              | Problem                                                                                                                                                        | Simpler recommendation                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lock a closed list containing `note`, `journal`, `template`, `playground`, `syntax`, `collection`, `effort`, `dashboard` first. | Mixes content semantics, placement, and creation workflows. The user specified `note` as the default; a separate `journal` type is not automatically required. | Inventory supported descriptors; decide what genuinely changes validation/configuration. Journal placement and provenance remain separate facts. Preserve unknown source rather than inventing an exhaustive future enum. |
| Every segment needs “exactly two renderings.”                                                                                   | Encourages duplicate edit/read component families and blocks content usable unchanged in both modes.                                                           | One content presentation where practical, with optional source-authoring controls and a CodeMirror adapter. Different host layouts may compose the same parts. Two modes do not require two implementations.              |
| Resolve all meanings of “segment” and rename the others.                                                                        | Runtime `segment`, storage `NoteSegment`, and `BlockIndexRow` are different responsibilities, not necessarily duplicate models.                                | Use qualified language in the crosswalk. Rename only when an actual interface is ambiguous; do not turn this map into a runtime/query vocabulary migration.                                                               |
| Graphs need additional segment types.                                                                                           | Reintroduces models that the dashboard already shares.                                                                                                         | Reuse `query` plus its presentation suffix. `query:timeseries` is already parsed as a query section; chart types and spans already live in a shared pure model [S2, S3].                                                  |
| WQL membership versus `pageId` is a single either/or decision.                                                                  | Query inclusion and owned placement answer different questions. Materializing query results creates synchronization and deletion questions unnecessarily.      | Keep owned placement distinct from discovery. | Effort unification requires a store merge or eliminating registry scans.                                                        | Domain identity does not determine physical storage. Decide authoritative linkage/update behavior first; add specific indexes only for required query semantics or measured cost.         |
| A read-only page must disable its embedded editors and widgets.                                                                 | Breaks syntax examples, local feed drafts, Run, inspection, and chart exploration.                                                                             | Prevent writes to the protected source while allowing explicitly supported local or runtime actions. Show where edits/results will be saved.                                                                              |
| Every future kind needs a generic registration platform.                                                                        | Adds a framework before there is a second real implementation of its extension interface.                                                                      | Extend the existing widget registry and editor extension mechanisms where they fit. New kinds earn their place with real content and real consumers.                                                                      |

**Best-practice basis:** composition and single-purpose components; minimal non-duplicated state; explicit data ownership; small interfaces hiding real complexity. React's [component decomposition](https://react.dev/learn/thinking-in-react) and [state-structure guidance](https://react.dev/learn/choosing-the-state-structure) support these choices. Atomic design is useful for reviewing reusable parts, not a reason to wrap every button or reorganize folders.

## 3. A smaller behavioral structure

Keep two crosswalks, not a giant type × widget × route × device × permission table:

1. **Note-type crosswalk:** configuration, default read/edit presentation, allowed source-authoring workflow, extra validation/projection.
2. **Segment crosswalk:** shared presentation, source-edit interaction, allowed non-source actions, unsupported/invalid state.

Apply shared precedence: **source authority limits writes; the selected mode controls authoring; note type supplies defaults; layout places the controls.** A type's “edit by default” must never grant write access to an immutable source. A multi-note page needs this evaluated against the actual owning note, not one page-wide permission flag.

| Action                                                                         | Recommended read presentation                                                                                         | Recommended edit presentation                                          |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Change note text, widget configuration, or query definition                    | No source mutation; offer Edit or an explicit personal-copy/draft workflow when supported.                            | Save to the identified note with validation and stale-edit protection. |
| Run a workout, inspect a query, follow a link, adjust a temporary chart filter | Allowed where the host supports it; these are not automatically source edits.                                         | Same reusable actions.                                                 |
| Save a result or capture an attachment                                         | Separate explicit operation with a known destination. “Read-only note” is not permission to write elsewhere silently. | Same destination rules.                                                |
| Try a syntax example                                                           | Edit a clearly scoped local example; original teaching source stays unchanged.                                        | Authoring the teaching source is a different operation.                |
| Persist dashboard filter defaults                                              | Explicitly distinguish this from a temporary filter.                                                                  | Persist only through the source-authoring path.                        |

Use the existing `ResponsiveActions` module rather than a new responsive-mode framework [S4]. Its children already become mobile overflow actions while rendering inline on desktop. The journal currently puts its toggle in `navbar`, so moving it into overflow is an intentional UX change, not a missing infrastructure capability. Preserve an obvious way out of editing, keyboard access, focus restoration, and visible save/error state. Desktop header placement remains the proposed presentation, not a domain field.

## 4. Reuse that the Playground can actually dogfood

The repo has useful reusable parts already. Consolidate callers around them before adding another “unified” layer.

| Existing reusable part                           | Real consumers / leverage                                                 | Recommended direction                                                                                                                                                                             |
| ------------------------------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WidgetChart`, `QueryBlockView`, `DashboardView` | Inline CodeMirror query blocks, dashboard cards, widget-composer preview. | Share query interpretation and chart presentation. Keep layout and explicit authoring callbacks outside the chart; do not rebuild an effort-only graph stack [S3, S5].                            |
| `EditorWindow`                                   | Canvas working panel, desktop scroll runway, mobile runway.               | Keep the existing editor/window module and slots; separate editable examples from page-source authoring [S6].                                                                                     |
| `SyntaxGroupWidget` and widget wrappers          | Playground landing content and widget-fence content.                      | A useful dogfood pattern: the same component renders ordinary page content and registered note content. Prefer this over duplicate page-specific markup.                                          |
| `ResponsiveActions` and existing page shells     | Journal, dashboard, other note pages.                                     | Declare actions once; reuse header/overflow placement. Do not make renderers own navigation chrome [S4].                                                                                          |
| `NoteEditor` and shared UI extensions            | Journal, effort detail, playground, feed items, example windows.          | Keep app persistence/navigation/runtime wiring in the host. Consolidate genuinely shared editor configuration into existing UI modules; do not keep expanding the host with note-type flags [S7]. |

Conceptually: existing controls → focused blocks such as query/result/example components → note presentation/editor composition → page layout → thin route host. This is a dependency direction, not a proposal for another mandatory hierarchy of wrappers.

A reusable module earns its place when the **same implementation** serves two real consumers and a fix benefits both. Storybook supplies isolated cases; it does not substitute for the real app using those components. A new widget should arrive with its authoring path, read presentation, invalid/unknown handling, and at least one real page using it—not a registry entry with no usable integration.

**Concrete reuse gaps to address—not new frameworks:**

- **Two editor recipes:** `editorPreset`'s markdown branch and `NoteEditor.baseExtensions` independently assemble overlapping extension sets [S7]. Make the production note host consume one shared recipe with app-only extras, rather than maintaining a separate demo recipe that is not dogfooded.
- **Two widget interpretation paths:** the in-flow widget reports invalid JSON, while `WidgetCompanion` silently substitutes an empty configuration [S12]. Share parsing/error semantics; keep overlay and in-flow layout adapters where they serve different interactions.
- **Home analytics is not yet full dashboard dogfood:** it imports chart primitives but duplicates query orchestration and a dashboard grid, including sample-data fallback [S13]. Reuse the production composition where it fits; supply clearly labeled teaching data through the existing executor/data seam. Do not make sample fallback a silent production-dashboard behavior or add a new results-provider framework just for the showcase.
- **Collections need more than a rendered query string:** the inline `FindResultList` currently renders text rows, not navigable note previews; dashboard grids explicitly refuse `find:` queries [S5, S13]. Reuse the relevant result-list presentation and host navigation callbacks without changing Library routes or coercing note listings into chart widgets.

## 5. Playground functionality crosswalk

| Surface                             | What unifies                                                                                             | What must remain distinct / risk                                                                                                                                                                             |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Journal / ordinary notes**        | Shared text, workout, query, and widget presentations; one authoring policy.                             | A date page contains several owning notes. Preserve note IDs, results, attachments, ordering, and correct save targets. Do not flatten ownership away [S8].                                                  |
| **Playground notes**                | Same note/segment components, with an edit-oriented default when allowed.                                | Run/reset/local-draft behavior and result destination. Trying an example must not mutate its seed source or lose results on transition.                                                                      |
| **Syntax / teaching pages**         | Authored notes compose prose, examples, and scrolling content; shared example/query components.          | Sticky layout, reduced-motion/mobile presentation, and live local examples are legitimate specialized behavior. CodeMirror need not own page-level scrolling or every static posting.                        |
| **Effort notes**                    | Shared authoring and content widgets, plus effort metadata validation and queries scoped to that effort. | The linked effort record belongs to its authored effort note. This does **not** mean creating a new effort for every workout note. Preserve slug/alias matching, derivation, and unresolved-effort behavior. |
| **Dashboard notes**                 | Same source composition, query documents, graph widgets, inspection and editing parts.                   | Dashboard configuration, grid placement, query scope, temporary controls versus persisted defaults. Current dashboard notes already use `query` fences; the old `dashboard` fence is retired [S3].           |
| **Collection pages / feed content** | Prose plus WQL-discovered content using reusable presentations.                                          | Source ownership, local scratch copies, dates and deterministic ordering. ## 6. Blockers and pain points

### Blocking before broad editable page composition

1. **Correct note ownership through edits.** `JournalDatePage` captures note boundaries as line offsets on load, then slices later content using those same offsets. An isolated reproduction inserted one line into the first of two notes; neither resulting save contained the inserted line [S8]. Recommendation: start with per-note editing, or require transaction-mapped boundaries if seamless whole-page editing is essential. Do not expand this behavior to arbitrary multi-note pages first.
2. **Source writes must be guarded, not just hidden.** Widget source saves and query source saves dispatch changes without a read-only check; widget Enter/blur/save paths also exist [S10]. Hiding the pencil is insufficient. Gate authoring entry points and the source-write operation, retain trusted document-loading paths, and independently check persistence ownership. This is an in-app correctness constraint, not a server authorization boundary.
3. **Source preservation and stable identity.** Preserve unknown fences, metadata, query attributes, ordering, and malformed drafts across editor → save → reopen → posting. Current persistence reconstructs workout/frontmatter delimiters and matches segments by ID or position/type, so byte-exact round-tripping is not an existing guarantee [S14]. Decide acceptable normalization explicitly. Occurrence identity must not be confused with same-content identity; two identical blocks may have different local state and result destinations. Protect stale edits as dashboard widget mutations already attempt [S11].

### Decisions needed for the reusable contract

4. **One source of truth across projections.** Define the owning note and atomicity/error behavior for effort properties and source edits; prevent seed refreshes from overwriting personal content. Do not let widget state, parsed properties, stored segments and markdown become independently writable copies.
5. **Interactive read views.** Decide temporary versus persistent dashboard controls, query inspection, local examples, and Run/result actions explicitly. The map currently treats some deliberate differences as bugs. Reuse depends on clear action semantics, not a universal disabled state.
6. **Editor lifecycle and accessibility.** Full `StateEffect.reconfigure` preserves the view, not necessarily every widget's draft, focus, media state, or query subscription. Equality checks currently omit some behavior-bearing inputs [S5, S7, S10]. Require preservation behavior before choosing remounts versus updates. Non-editable CodeMirror content also needs deliberate keyboard/focus behavior; see the [read-only example](https://codemirror.net/examples/readonly/).
7. **Dynamic query scope and cost.** Explicitly scope embedded queries to the intended note/effort/date; preserve Query Document isolation. Collections that embed other notes need a recursion policy. Many live queries/editors can multiply work—this is an unmeasured risk, not evidence for a cache, pagination framework, or new index now. Prefer result previews over nested editable documents unless editing is required.
8. **Trust and recovery.** Imported widget/config source needs validation and existing URL/content sanitization. Unknown widgets and invalid metadata must remain inspectable and recoverable without discarding original source. A type descriptor or tag must not grant authoring privileges.

**Concrete storage constraints behind those blockers:**

| Current fact                                                                                                                                                                 | Simplification / required decision                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Seed import assigns a deterministic note ID from the source path and a seed-build timestamp; static-note projection instead uses the block index's `noteId` and date [S15].  | Define canonical ownership identity separately from external locators, and authored/journal dates separately from import time. Do not claim content sources unify merely because their rows look alike. Preserve existing Library locator behavior when changing joins.                   |
| Bundled effort import creates notes plus parsed effort records; the user-edit path saves parsed properties through `registry.upsert` [S15, S16].                             | Efforts remain notes in the domain. The unresolved implementation detail is explicit ownership/linkage and consistent update direction across sources—not whether efforts qualify as notes. Keep the registry; define how the owning note and its parsed projection are updated together. |
| Editor query/widget kinds need not equal persisted kinds: persistence maps workout sections to `wod`, headings to heading kinds, and remaining sections to `markdown` [S14]. | Use the crosswalk to connect source grammar, editor sections, stored segments and query projections. Do not require a storage-enum migration merely to support a new query-chart presentation.                                                                                            |
| `deleteNote`'s transaction omits `block_index`; the legacy UUID re-key transaction omits it and tag/field stores [S17].                                                      | Specify deletion/re-key consistency before trusting reusable WQL collection views. These omissions are source facts; user-visible stale-search impact was not exercised here. Derived data must follow ownership changes rather than become permanent parallel truth.                     |

## 7. Review of the wayfinder itself

**Good:** plan-only destination; child issues; human decisions separated from research; explicit Library exclusion; a crosswalk instead of an implementation sprint.

**Needs correction:**

- The Destination preselects a closed type set and “exactly two renderings” while tickets are meant to decide those questions. Record these as candidates, not locked architecture. Likewise, desktop-toggle wording was tentative; do not turn every suggestion into an immutable constraint.
- Current facts are stale in places. The [dashboard glossary](../../CONTEXT.md) and shared model retire the `dashboard` fence. Feed scratch edits and syntax examples are intentional. The closed research is useful evidence, not a full permission/lifecycle design: an explicit option does not itself protect writes, and checking a source-write facet need not disable Run or filters.
- **The visual frontier is not wired.** Live inspection found nine child issues, eight open, one closed, thirteen body `Blocked by:` edges, and **zero native dependency edges**. GitHub's native `dependencies/blocked_by` API returned HTTP 200. Migrate approved edges to [native issue dependencies](https://docs.github.com/en/rest/issues/issue-dependencies); the map's “no native dependency relationship” assertion is wrong. This review did not mutate the graph.
- The type ticket is an unnecessary gate for general authoring safety. Establish invariants while type naming proceeds; only type-specific default rows require the taxonomy decision.
- “How do we add a supported segment using the same authoring and reading components?” and “How do we preserve owning-note identity across page edits?” are sharp questions now—not distant fog. Fold them into existing segment/crosswalk questions; do not create a framework-building workstream.
- Keep the map as a short index. Maintain one resolution per ticket, a glossary for terms, and a crosswalk for the adopted contract. Do not restate the same rationale in all three. Review recommendations stay outside Decisions-so-far until adopted.

## 8. Dogfood acceptance scenarios for the eventual implementation

Use real seed/user notes and the existing Playground routes. No new component-gallery application is needed.

- **Journal:** two notes on one date; insert/delete/reorder near their boundary, save/reopen, run the second note, and confirm text/results still belong to the right UUID.
- **Syntax:** the same runnable example component in a teaching page and a Playground note; edit locally, reset, run, and preserve source; check mobile, desktop, reduced motion, and keyboard exit.
- **Effort:** edit valid properties, reject invalid properties without losing the draft or publishing an invalid registry entry; the same query/chart component scopes to the effort without an effort-specific renderer.
- **Dashboard:** the same query presentation inline and in the grid; inspect/filter in read presentation without rewriting source, explicitly persist defaults, then edit/reorder safely with duplicate queries and stale drafts.
- **Collection/feed:** prose plus a query listing; empty results, dates and ordering, opening a result, and local scratch edits behave predictably. Existing Library results and deep links do not change accidentally.
- **Mixed-content note:** text, workout, query chart, known widget and unknown fence; edit/view/reopen preserves source and errors. Read presentation has no authoring write path through pencil, Enter, blur, paste or drop, but allowed Run/inspection still work.

A component is successfully dogfooded when these pages consume its production implementation—not when a story imports a parallel mock.

## 9. Evidence and verification

Ran two throwaway Bun probes, with no application mutations:

- Real `@codemirror/state`: `readOnly` remained true while a programmatic transaction changed `original` to `programmatic`. Real `sectionField` parsed a heading, `query:timeseries`, and `widget:attention` as `markdown`, `query`, and `widget` respectively.
- Isolated reproduction of `JournalDatePage`'s boundary-slicing algorithm: `Alpha\n\nBeta` edited to `Alpha\nAdded to Alpha\n\nBeta` produced saves `Alpha` and `Beta`; the inserted line was absent. This exercises the algorithm, **not the live browser or persistence**.

Read all child question bodies and queried native dependency state. No full application test, browser interaction, storage migration, performance benchmark, or security audit was performed. Component lifecycle, rendering parity, and scale concerns above are risks to exercise, not claimed runtime failures.
